# Changelog

All notable changes to `ocfl-cli`. Format: [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).
No release is published yet, so every entry below is unreleased and may still change.

## [Unreleased]

### Exit 75 (ADR-0006)

- New exit code 75, "still pending": a one-shot `stage upgrade` or `stage batch upgrade` (no `--watch`) whose pass left proofs not final exits 75 (was 0). It is a result, not an error: nothing on stderr, and `--json` prints the usual document. Everything else keeps its code: `stage timestamp` after a submit, a verb with nothing to do, and `--watch` exit 0. The exit codes are 0, 1, 2, 3, 4, 5, 6, 75, 130 (`ExitCode.PENDING`).

### Validate (issues 16 and 34 of docs/cli-surface-review.md)

- `ocfl validate --ots=auto|local|chain` replaces default-on `--verify-ots`. `auto` (the default) checks the OTS proofs against Bitcoin when `[bitcoin]` is configured and otherwise runs the local checks and says so on stderr (it was exit 6). `chain` needs `[bitcoin]` (exit 6 without). `local` never asks a node. Every mode runs the extension's own checks; there is no mode that skips them.
- Root-level `ocfl validate` checks every object's proofs against Bitcoin too (it ignored the chain).

### CLI surface (docs/roadmap.md §7)

- Verbs instead of mode flags: `stage timestamp OBJ`, `stage upgrade OBJ [--watch]` and `stage retry OBJ` replace `stage timestamp content|inventory OBJ [--upgrade [--watch] | --retry]`. The Timestamp Target comes from the Phase; `--expect content|inventory` asserts it (a mismatch is still exit 3). `--watch` means the same on both verbs: do the verb, then upgrade on each block until the target's proofs are final. `stage timestamp --allow-missing-metadata` is the only place that flag exists. The old forms are gone (no release was published, so no aliases); so are the flag-combination usage errors.
- A verb with nothing to do in the Phase exits 0 and says what to run next (`stage upgrade` at drafting or content-upgraded, `stage retry` with nothing failed or outside a pending Phase, `stage timestamp` at inventory-upgraded); a phase error now ends with `; next: <command>`. `stage commit` at the wrong Phase names the real next command instead of always `stage timestamp inventory`.
- Batches are `stage batch create content|inventory OBJECT... [--objects-file F] [--category N] [--allow-missing-metadata] [--watch]`, `stage batch submit|upgrade [--watch]|retry|commit BATCH`, `stage batch status BATCH [--detail]`, `stage batch ls` and `stage batch rm BATCH [--force]`. They replace `stage timestamp batch content|inventory [--object ...] [--batch ID] [--upgrade|--retry|--watch]`, `stage timestamp batch ls|status|rm` and `stage commit --batch ID`. A resumed batch takes its target from its file. `batch status --verbose` is `--detail` (it shadowed the global `-v/--verbose`). `--allow-missing-metadata` on a content batch is a usage error. The batch file format is unchanged.
- `--json` covers the single-object verbs: a one-shot verb prints one document (`object_id, verb, target, phase_before, phase_after, done, idle, next` plus `submitted`, `pending`/`unrequested` or `retried`); `--watch` prints NDJSON events (`block`, `advanced`, `already_advanced`) ending in a `summary` event. They printed human text even under `--json`.
- Every next-step hint is a full command with the object or batch id, built in one place (`workflow.hints`): `stage status` `next_action` (e.g. `ocfl stage upgrade OBJ --watch`), the verbs' `Next:` line, batch rows' `next` (e.g. `ocfl stage batch retry ID`) and error hints. `next_action_kind` is unchanged.
- The phase FSM's command names follow the verbs (`timestamp|upgrade|retry content|inventory`; the `--watch` variants are gone); `model.phase.is_legal` asks without raising. `workflow.timestamp` gained `idle`, `check` and `next_step`; `retry` returns `retried=0` instead of raising `NoFailedSubmissionsError` (removed); results expose `done`.
- `stage reset` is `stage discard` (it deletes the Staging Area; `reset` means something else in git). Same rules: `--force` to drop persisted OTS progress, and nothing staged exits 0 with a note on stderr. The FSM command is `discard`; a v1 `ots.json` points to `stage discard --force`. `workflow.staging.reset_staging` is `discard_staging`.
- New `ocfl config path` (config file, secrets file, staging root; `--json` adds whether each exists), `ocfl config show` (the effective config, every secret shown as `<redacted>`) and `ocfl config check` (config, `.env` mode, SimpleProof access token, Bitcoin RPC, a TCP or socket-path probe of the ZMQ endpoint). `check` exits 6 when the config or a credential is wrong and 1 when a service cannot be reached; `--json` prints `{"ok", "checks": [{"name", "ok", "detail", "error_class"?}]}`. `config path` and `config check` run on a config that does not load (they report it); every other command still exits 6, but `--help` and usage errors come first (exit 0 and 2). New errors `ConfigCheckFailedError` (exit 6) and `ServiceCheckFailedError` (exit 1).
- The SimpleProof client port has `check_access()` (`GET /api/entity/proofCategories` with the access token; the API key has no read-only endpoint, so it is not checked). `config.check_env_file` (was `_check_env_file_perms`), `config.redacted`, `config.user_env_file_path` and `ots.bitcoin.probe_zmq_endpoint` are new public helpers.
- Locks (ADR-0005): every CLI lock is an exclusive `flock` (`store.locks.flock`), waited on for `Runtime.lock_timeout`, now 5 s (was 30 s), through the `Sleeper` port, then exit 4 (`lock_timeout`). The batch lock `batches/<id>.lock` is held for a whole batch run and is the lease: a second driver, `stage batch commit` or `stage batch rm` of the same batch exits 4 after 5 s. The `.driver` lease file, its heartbeat thread, refresh lock, stealing and signal handlers are gone (`DriverLease`, `with_driver_lease`, `with_batch_lock`, `installed_cli_version` removed from `store.batch`), and so is the `filelock` dependency. `with_lock`, `object_commit_lock` and `batch_lock` take the `Runtime`. A lock held by a process that died is free at once.
- `stage batch rm` deletes the batch's lock file too (and leaves no `.driver*` files, which no longer exist).
- The 37 issues of the old CLI surface review each have a decision (adopt or reject, and why) in `docs/cli-surface-review.md`. Beyond the items above, these changed:
  - `stage upgrade --watch` (and `stage timestamp --watch`) runs one upgrade pass before the first block, so proofs that are already final do not wait for one.
  - `stage batch create inventory --from C_ID` takes the objects a content batch upgraded.
  - Batch ids accept a unique prefix (an ambiguous one is exit 2, an unknown one exit 1).
  - A batch row for an object with no Staging Area is skipped as `not_staged` (was `committed`), one with a plain Staging Area as `not_ots`; `stage batch create|submit` then exit 1 (`objects_not_staged`) naming them, and the rows' `next` says how to stage them.
  - `ocfl purge -y/--yes` skips the prompt; `--force` is gone. `ocfl log -n/--limit`. `stage rm -R/--recursive` replaces `-r`.
  - `ocfl ls` and `ocfl export` take `-V/--object-version` (was `-V/--version`); `ocfl --version` prints the program version.
  - `stage new --digest` offers sha512 and sha256 only (the other choices were refused anyway).
  - `stage ls OBJ --json` is always `[{"path"[, "digest"]}]`; `stage ls` with no object lists the root's Staging Areas (`[{"object_id", "phase"}]`, phase null for a plain one).
  - At `stage commit`, a missing, unverified or uncached inventory proof or a stale plan is exit 3 (`inventory_proof_missing`, was 5); exit 5 is left for a cached proof that does not parse or commits to other bytes, and its help reads "operator review". A missing batch is exit 1 (`batch_file_missing`, was 2); committing a content batch or another root's batch is exit 3 (`batch_mismatch`, was 2).
  - A `[simpleproof]` or `[bitcoin]` section that does not load (e.g. a missing secret) fails only the commands that need it (`Config.raise_if_broken`); `ocfl ls` and the other read commands run. `config show` lists the section errors and `config check` fails them (exit 6).
  - `ocfl export --to -` with more than one matching path is a usage error (exit 2); it wrote only the first.

### Merged timestamp workflow (docs/roadmap.md §6)

- One timestamp workflow for both Timestamp Targets: `workflow.timestamp` (`TimestampRun`; `submit`, `upgrade`, `retry`, each with `expect=None`) and one `workflow.watch.watch` loop replace `workflow.content`, `workflow.inventory`, `watch_content` and `watch_inventory`. The target comes from the Phase (`model.phase.TimestampTarget`, `target_for`); `stage timestamp content|inventory` pass it as `expect`, and a mismatch is still a phase error (exit 3). What differs between the targets lives in `workflow.targets` (`TargetRules`: `CONTENT`, `INVENTORY`), which the batch engine uses too; `BatchFile.target` is a `TimestampTarget` (the batch file format is unchanged).
- An inventory submission is recorded in `ots.json` like a content one (`Submission(target="inventory")`, `submitting` before the POST, `submitted` after), and `plan.json` is written before the POST. A failed POST leaves content-upgraded with the intent; the next `stage timestamp inventory` resends it. Inventory batch ids and record ids live on that submission (`inventory.batch_id`/`record_id` are gone).
- `stage timestamp inventory` at inventory-pending no longer re-sends a digest that was already submitted (as for content). `stage timestamp inventory --retry` re-sends only `failed` submissions and prints `no failed submissions to retry` when there are none (it always re-sent the digest).
- Upgrade job progress lists only the jobs that cover the target's proofs. An inventory batch row moves its object to inventory-pending once its record ids are mirrored (like content). Another batch blocks an object only while its submission of the same target still waits for a proof.
- `ots.json` schema 2 (ADR-0004): one `proofs` table `{digest: {target, ots_path, verified, …}}` for content and inventory proofs replaces `content_proofs` and `inventory_proof`; the staged inventory is `inventory: {version, digest, …}`; every submission records its `target`. A v1 `ots.json` is refused (no migration before launch): discard the staging with `stage reset --force` and stage again. `stage reset` counts `proofs=` instead of `content_proofs=`/`inventory_proof=`.
- Proofs are kept by digest when a Staging Area moves back (`add`/`rm`/`mv`, metadata edits): verify jobs, cached `.ots` bytes and `plan.json` stay too. A removed-and-re-added, renamed or changed-back file reuses its proof (no new submission), and `stage timestamp content` moves straight to content-upgraded when every needed digest is final. A rebuilt inventory with the same bytes reuses its proof and moves straight to inventory-upgraded. Fixes a re-added file that held content-pending forever as an "orphan".
- `X.ots` is a content proof only when `X` is in the same state (`ocfl_lib.ots.split_state`): a standalone `x.ots` is submitted and gets `x.ots.ots`, and `rm`/`mv` of it move its companion. Every path of a digest gets its companion (only the first did, so the commit was refused with E902). A file re-added to a new version of an OTS object reuses the object's committed proof of its digest; one re-added to a plain object's first OTS version is submitted (both were skipped because their digest was in the manifest, so the commit was refused with E902).
- `commit_bare` and `commit_ots` share one execute/revert block (`workflow.commit`): object lock, staging lock, prepare, commit, purge. The OTS path now holds the staging lock through the commit and purge, as the plain path did, so staging cannot change between the checks and the purge; a `--watch` on the same object waits for the lock and retries on the next block.

### Layers (ADR-0003)

- `ocfl_cli` is layered commands → use cases → adapters, and import-linter enforces it (`uv run lint-imports`; contracts in the root `pyproject.toml`). Commands: `main`, `archive`, `stage`; use cases: `workflow`; adapters: `ots`, `store`; base: `model`, `ports`, `config`, `errors`. No behavior or output change.
- Modules moved: `stage.service` and `stage.watch` → `workflow.{staging,status,content,inventory,commit,common,watch}`; `stage.commands` → `stage.{_app,edit,status,commit,timestamp,batch,render}`; `stage.{store,state,_wire,batch,ingest}` → `store.{staging,ots_state,_wire,batch,ingest}` with their value types in `model.{ots_state,batch,content}`; `stage.{fsm,schemas}` → `model.{phase,metadata}`; `config`, `archive.config`, `ots.config` → `config`, `config.archive`, `config.ots`; the `BitcoinRPC`, `HashBlockStream` and `SimpleProofClient` Protocols and the client factory types → `ports`; SimpleProof result types → `model.simpleproof`.
- The batch engine moved from `stage.batch` into `workflow.batch` (`drive`, `prepare`, `submit`, `retry`, `upgrade`, `watch`, `report`, `reasons`). Its drivers report through a `BatchEvents` Protocol that the command renders; batch files, leases, events and output are unchanged.
- Ports for time (`ocfl_cli.ports`): `Clock`, `Sleeper` and `BlockStream` (ZMQ `hashblock`), with `ocfl_cli.system` as the only module that reads the real clock or sleeps. `AppCtx` carries `clock`, `sleeper`, `block_stream_factory` and `lock_timeout`, and the use cases receive them as one `ports.Runtime`. Tests inject fakes under the same `ctx.obj` keys instead of patching module internals. The SimpleProof client port states its `submit_chunk_size`; batch `drive.commit` takes the per-object commit as a `commit_object` dependency. No output or format change: batch files, `ots.json` and lease timestamps come from the injected clock.
- `AppCtx.fs_factory` (port `ports.FsFactory`, default the lib's `open_fs`) opens the storage root's filesystem for every command, so tests inject a faulting filesystem instead of patching the commit's content source.
- Helpers used across modules lost their leading `_` (e.g. `object_commit_lock`, `upgrade_content`, `SUBMIT_CHUNK_SIZE`); no module imports another's `_name`, and no test uses a `_name` (tests may import a package-private `_module`). Helpers that tests exercise are public: `should_color`, `configure_logging`, `installed_cli_version`, and the `render_*` / `emit_root_object_results` renderers.

### Output

- Each command run makes its own stdout and stderr consoles (`AppCtx.console`, `AppCtx.err_console`), coloured from that run's `--no-color`, `NO_COLOR`, `FORCE_COLOR` and TTY. `_style` keeps no consoles: `--no-color` no longer leaks into later runs in the same process, and `FORCE_COLOR`/`NO_COLOR` are read per run instead of at import. Removed `_style.echo`, `set_no_color` and `reinit_from_env`; use `_style.make_console`.

### Errors and exit codes (docs/roadmap.md §5)

- One error handler at the root command group. Commands raise; the handler prints the error and exits. Every CLI error carries an `ErrorClass` and a stable snake_case `code`, like the lib's errors, and `exit_codes.exit_code_for_class` maps the class to the exit code with one exhaustive `match` (ocfl-rs ADR 0004): `NOT_FOUND`, `INVALID`, `SERVICE` → 1; `USAGE` → 2; `STATE` → 3; `BUSY` → 4; `HALT` → 5; `CONFIG` → 6; `INTERRUPTED` → 130. The documented exit codes are unchanged; `--help` now names the error classes each one covers (e.g. 3 is any state error, 4 any held lock).
- Under `--json`, an error is one JSON line on stderr, `{"error": {"code", "message", "exit"}}`, and stdout stays empty. Text mode still prints `Error: <message>` on stderr.
- `ocfl validate --json` with an unreachable Bitcoin node now reports the failure as a JSON error on stderr (`code` from the lib error, e.g. `bitcoin_rpc_transient`); it still exits 1 and never reports E906 for a node failure. Text mode still prints `Error: cannot verify OTS attestations: …`.
- `validate --json` reports a root or object it cannot open as a JSON error on stderr instead of `{"valid": false, "errors": [<message>]}` on stdout.
- `stage timestamp batch … --batch ID` with no batch file: under `--json` the error is the stderr JSON error (`code` `batch_file_missing`, exit 2) instead of `{"batch_id", "reason", "next"}` on stdout.
- Lib errors that reach the CLI now exit with their class's code instead of 1: e.g. `init` on an existing root (`root_exists`, STATE) exits 3, a busy object lock (`object_locked`, BUSY) exits 4, `recover` with an action that does not apply (`recovery_action`, USAGE) exits 2, a bad layout config or unsupported backend (CONFIG) exits 6, and a Bitcoin RPC auth failure (`bitcoin_rpc_auth`, CONFIG) exits 6. A SimpleProof auth failure (`simpleproof_auth`) is CONFIG too and exits 6 (was 1), so both credential failures exit alike.
- Errors that used to escape as a Python traceback with exit 1 now go through the handler too: e.g. a held batch driver lease (`lock_timeout`) exits 4, an `OSError` exits 1 with `Error: …`, and an uncaught Ctrl-C exits 130 instead of click's `Aborted!` with 1.
- A staged `inventory.json` that is not valid JSON or not an inventory is a `staging_error` naming the file (exit 1), as a corrupt staged `metadata.json` already was. Before, every `stage` command on that object printed a msgspec traceback.
- The CLI uses the lib's Bitcoin RPC client and errors (`ocfl_lib.bitcoin.BitcoinRpcClient`, `BitcoinRpcError` and subclasses) directly. Removed `BitcoinRPCClient` and the CLI's `BitcoinError`, `BitcoinAuthError`, `BitcoinRPCTransient`, `BitcoinBlockMissingError` and `BitcoinUnavailable`.
- New errors: `UsageError` (exit 2), `ErrorContext` (adds context to another error's message and keeps its class and code), `BatchFileMissingError`, and `CommitFailedError` subclasses `CommitClaimLostError` (exit 3) and `CommitInterruptedError` (exit 130), which replace its `claim_lost` / `interrupted` flags.
